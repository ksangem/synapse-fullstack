carries meaning, (2) a type scale with no scale, (3) three fake/dead UI surfaces that a buyer will
find in the first two minutes, and (4) near-zero semantic HTML.

## Severity 1 — Credibility. A prospect finds these in the first 2 minutes.

### 1.1 The notification bell is entirely fabricated data
`components/layout/NotificationDropdown.jsx:4-35` is a hardcoded array:

> "SAP ERP Adapter Down" · "Salesforce token expires in 3 days" · "High latency on Workday sync"
> · "New connector published: Stripe v2.1" · "Weekly performance report ready"

Synapse connects to **none** of SAP, Salesforce, Workday, or Stripe. The header count
`<span className="badge-count">3</span>` (`Topbar.jsx:216`) is a literal `3` — it never changes, never
clears, and never reflects the real alert count. `notif-header` likewise hardcodes "3 unresolved".

This is especially damaging because `CriticalBanner.jsx` **does** poll real alerts correctly
(`api.getAlerts('?resolved=false&severity=critical')`, 30s). So the app shows a real critical banner
and a fake notification tray side by side. Wire the dropdown to the same endpoint and derive the badge
count, or remove the bell.

### 1.2 The browser tab says `synapse-react`
`index.html:8` — `<title>synapse-react</title>`, the Vite scaffold name. There are only 3 `document.title`
writes in the whole app, none of them per-page. Every tab, every bookmark, every screenshot a customer
takes is labelled with the scaffold name. Enterprise apps set `Synapse — <Page>` on every route.

### 1.3 A cursive handwriting font is downloaded from Google on every page load — and never used
`index.html:7` render-blocks on `fonts.googleapis.com/css2?family=Dancing+Script`. `Dancing Script` appears
nowhere in `styles.css` or any component; the app uses a system font stack. So this is a dead
render-blocking third-party request that also leaks visitor IPs to Google on every load — a real
procurement/GDPR question for an enterprise buyer. Delete the line.

### 1.4 14 of 31 toolbar buttons are non-functional
`data/toolbarConfig.js` marks `todo: true` on 14 buttons. They render at `opacity: 0.6`, are fully
clickable, and respond with a toast saying the feature "isn't available yet".

| Page | Dead / total |
|---|---|
| **Alerts** | **3 / 3 — the entire toolbar** |
| Canvas | 3 / 6 |
| Registry | 2 / 4 |
| Studio | 2 / 3 |
| Catalog | 2 / 3 |
| Vault | 1 / 3 |
| Admin | 1 / 3 |

The Alerts page presents a toolbar where nothing works. Hide unbuilt actions rather than shipping them
greyed-out; `opacity: 0.6` reads as "disabled for now", not "not built".

### 1.5 Scaffold and template leftovers ship in the build
- `public/icons.svg` — 12 symbols: **Bluesky, Discord, GitHub, X (Twitter)**, social, documentation.
  Never referenced anywhere. Publicly served at `/icons.svg`.
- `src/assets/react.svg`, `vite.svg`, `hero.png` — unused scaffold assets.
- `public/favicon.svg` is `#863bff`; the app's `--primary` is `#6366f1`. The tab icon is a different
  purple from the product.

### 1.6 The logo is a 596 KB PNG rendered at ~120 px
`nalashaa-logo1.png` is **1089×347, 596 KB**, displayed at `width: 50%` of a 240px sidebar. It is
92% the size of the entire 642 KB JS bundle (`dist/assets/`). It has no `width`/`height` attributes
(layout shift) and is raster (soft on HiDPI). Should be an inline SVG at ~5 KB.

Worse, `styles.css:157`: `.sidebar.collapsed .nalashaa-logo-img{width:90%}` — in the 64px collapsed rail
the full wordmark renders at ~57×18px, an illegible smear. The standard pattern is mark-only when
collapsed, wordmark when expanded.

### 1.7 One JS chunk, no code splitting
`dist/assets/index-*.js` is a single **642 KB** bundle. The 3,979-line `WizardPage` and 1,080-line
`StudioPage` are parsed before the login screen paints. `React.lazy` per route is a one-hour change.

## Severity 2 — Color theme. The palette fails WCAG wherever it carries meaning.

Computed contrast ratios (sRGB, WCAG 2.1). AA needs **4.5:1** for text, **3:1** for large text and for
UI component boundaries (1.4.11).

### 2.1 Status colors are unreadable in light theme — and status is the product
| Pair | Light | Dark |
|---|---|---|
| `badge-success` text on `--success-dim` | **2.09** ❌ | 5.80 ✅ |
| `badge-warning` text on `--warning-dim` | **1.99** ❌ | 6.08 ✅ |
| `badge-error` text on `--error-dim` | **3.29** ❌ | 3.90 ❌ |
| `badge-info` text on `--info-dim` | **3.29** ❌ | 3.82 ❌ |
| `badge-primary` text on `--primary-dim` | **3.95** ❌ | 3.25 ❌ |

An integration platform's core UI vocabulary is *success / warning / error*. In light theme a green
"Active" badge sits at **2.09:1** — worse than light-grey-on-white. The cause is using the *same* hex
for both the tint and the text: `--success:#22c55e` painted at 10% opacity as the background and at
100% as the text. Dark theme largely survives (15% tints over a dark base darken the field); **light
theme is the broken one.**

Fix: split the token. Light theme needs a separate darker on-tint value per status
(e.g. `--success-on:#15803d`, `--warning-on:#b45309`, `--error-on:#b91c1c`, `--info-on:#1d4ed8`) while
keeping `#22c55e` etc. for dots, bars, and dark theme.

### 2.2 Solid semantic buttons fail too
| Button | Ratio | |
|---|---|---|
| `.btn-success` — white on `#22c55e` | **2.28** | ❌ both themes |
| white on `--warning` `#f59e0b` | **2.15** | ❌ |
| `.btn-danger` — white on `#ef4444` | **3.76** | ❌ |
| `.btn-primary` — white on `#6366f1` | **4.47** | ❌ (misses 4.5 by 0.03) |

`--success` and `--warning` are *fill* colors being used as *button* colors. `#22c55e` and `#f59e0b`
can never carry white text. Either darken the button variants or switch those two to dark text.

### 2.3 `--text-dim` fails everywhere it is used — including every table header
`styles.css:259` sets `th { color: var(--text-dim) }`, and `thead th` sits on `--bg-input`.

| Context | Light | Dark |
|---|---|---|
| `--text-dim` on `--bg-input` (**every `<th>` in the app**) | **2.34** ❌ | 3.90 ❌ |
| `--text-dim` on card | **2.56** ❌ | 3.58 ❌ |
| `--text-dim` on page bg | **2.16** ❌ | 4.00 ❌ |

`--text-dim` is used for table headers, KPI sub-labels, timestamps, `.tile-meta`, `.notif-meta`,
`.chart-foot`, form hints, and the `.empty-state` copy — i.e. most of the app's secondary text.
`--text-secondary` (4.76 light / 6.65 dark) passes; `--text-dim` should be retired or darkened to
roughly `#5b6b7f` (light) / `#8b9bb0` (dark).

### 2.4 Borders are invisible — every card, table, input, and panel edge fails 1.4.11
| Boundary | Ratio (need 3.0) |
|---|---|
| Light `--border #d8d0f0` on card | **1.48** |
| Light `--border` on page bg | **1.25** |
| Dark `--border #2a2a45` on card | **1.23** |

Every structural edge in the app — `.card`, `.table-wrap`, `input`, `.panel`, `.modal-dialog`, all `td`
dividers — is below half the required contrast. This is why the UI reads as "soft" rather than
"enterprise dense": the grid structure is technically there but visually absent.

### 2.5 Cards do not separate from the page, and hover feedback is imperceptible
| | Ratio |
|---|---|
| Light card `#ffffff` on page `#ede9fe` | 1.19 |
| Dark card `#1a1a2e` on page `#0f0f1a` | 1.12 |
| `--bg-card-hover` vs `--bg-card` (light) | **1.10** |
| `--bg-card-hover` vs `--bg-card` (dark) | **1.11** |
| `tr:hover` — `rgba(99,102,241,.03)` on a white row | **1.04** |

`styles.css:261` — `tr:hover td{background:rgba(99,102,241,.03)}` at **3% opacity** is effectively
invisible. In a dense ops table, row hover is the primary "which row am I on" affordance. Take it to
6–8%. Likewise `--bg-card-hover` differs from `--bg-card` by 1.1:1 — every list-row, tree-item,
accordion, notification, and help-article hover state in the app is functionally a no-op.

Also: in light theme `--bg-card-hover` and `--bg-input` are **the same value** (`#f5f3ff`), so a hovered
row is indistinguishable from an input field.

### 2.6 Dark theme has no elevation model
`--bg-sidebar` and `--bg-card` are both `#1a1a2e` — identical. The sidebar, the cards, the topbar, and
the modals are all the same plane, separated only by 1.23:1 borders. Nothing recedes or advances.

### 2.7 The two themes are different products
Light theme: lavender page (`#ede9fe`), deep-purple sidebar (`#1e1245`) with **peach** text
(`#fcd5b5`, `#c9a882`, active `#ffe4c9`, active border `#fbbf94`).
Dark theme: the sidebar aliases straight to `--text` / `--primary` — no peach at all.

So the brand's sidebar identity — purple + peach — exists only in light mode, and there is no peach
token anywhere in the dark palette. Also, `#ede9fe` (Tailwind violet-100) as the *default page
background* is a saturated tint, not an enterprise neutral; it is what makes the whole light theme
read as a consumer app. The sidebar contrast itself is the one genuinely good part of the palette
(7.66–12.48:1, all passing).

### 2.8 Color is the only status channel
`.status-dot` is an 8×8 px dot with `.green` / `.amber` / `.red` and no icon, shape, or text. Deuteranopic
users cannot distinguish `--success #22c55e` from `--warning #f59e0b`. WCAG 1.4.1. Pair each dot with a
glyph or a text label.

### 2.9 99 hardcoded colors bypass the theme
`grep` finds 99 raw hex values in JSX. Notable:
- `WizardPage.jsx:3705` — `background:'#1a1d2e', color:'#e2e4f0'`: a **hardcoded dark** code block that
  stays dark in light theme.
- `DashboardPage.jsx:199,203,371-373` — chart colors `#ef4444 / #f59e0b / #22c55e / #6366f1` hardcoded,
  so charts never respond to the theme.
- `mappingUtils.js:88` — `PAIR_COLORS`, 10 hardcoded hues, duplicated again as `.mp-c1`–`.mp-c10` in CSS.
- Off-palette values that exist in no token at all: `#2ea043`, `#c0392b`, `#d9821a`, `#e66`, `#3a3`, `#4f7`.

### 2.10 Four CSS variables are used but never defined
`--danger`, `--bg`, `--bg-alt`, `--primary-soft` are referenced in JSX and defined nowhere in `styles.css`.

Most consequential: `JoinsPanel.jsx:25` — `background: 'var(--bg)'` with **no fallback**. The declaration
is invalid, so every input in the Joins panel falls back to transparent while every other input in the
app is `--bg-input`. `PresetConfigFields.jsx:82` and `CrawlRecorder.jsx:425` use `var(--danger, #ef4444)`
and `var(--danger, #e66)` — always the hardcoded fallback, and the two fallbacks are different reds.

## Severity 3 — Typography. There is no type scale.

### 3.1 30 font sizes in CSS, 26 more inline — 441 inline `fontSize` declarations
CSS uses 30 distinct `font-size` values. JSX adds 441 more inline declarations across 26 distinct values.
The set includes `.55, .58, .6, .62, .65, .66, .68, .7, .72, .74, .75, .76, .78, .8, .82, .84, .85, .88, .9, .95` —
twenty steps between 0.55rem and 0.95rem. `.74` vs `.75` vs `.76` are three separate tokens for a
0.3 px difference. There are **no `--font-*` tokens at all**, so there is nothing to standardise on.

An enterprise scale is 6–8 steps: e.g. `--fs-xs .75 / --fs-sm .8125 / --fs-base .875 / --fs-md 1 / --fs-lg 1.125 / --fs-xl 1.375 / --fs-2xl 1.75`.

### 3.2 13 of those sizes render below the 12 px legibility floor
`html{font-size:clamp(15px, 0.5vw+11px, 18px)}` — so on a phone/small laptop the root is 15 px:

| rem | @15px root | @18px root |
|---|---|---|
| `.55` | **8.3 px** | 9.9 px |
| `.6` | **9.0 px** | 10.8 px |
| `.65` | **9.8 px** | 11.7 px |
| `.68` | **10.2 px** | 12.2 px |
| `.72` | **10.8 px** | 13.0 px |
| `.75` | **11.3 px** | 13.5 px |
| `.78` | **11.7 px** | 14.0 px |

`.72rem` alone appears 15× in CSS and 48× inline — that is the size of `.badge`, `.tile-route`,
`.notif-meta`, `.detail-pane-breadcrumb`, `.countdown`, every editor field label. At 15px root those are
**10.8 px**. `.55rem` (`.mapping-field .map-num`) is **8.3 px**. `.6rem` (`.confidence-inline`, 11 inline
uses) is **9 px**. Nothing informational should render below 12 px; 13 of 20 sub-1rem steps do on a
15px root.

### 3.3 Body text is `.85rem` — small for a data product
`button`, `td`, `.nav-item`, `input`, `.tab-btn`, `.user-name`, `.help-article` all sit at `.85rem` =
**12.8 px** at 15px root. The default `<button>` rule (`styles.css:71`) forces `.85rem` on every button
in the app, including `.btn`, which declares no size of its own.

### 3.4 Four different monospace stacks
- `.help-code code` → `ui-monospace, SFMono-Regular, Menlo, Consolas, monospace`
- `.json-block` → `'Consolas','Monaco',monospace`
- `.expr-editor` → `'Consolas','Monaco','Fira Code',monospace`
- 43 inline `fontFamily: 'monospace'` (bare keyword)

The JSON payload viewer, the expression editor, and the help code blocks each render in a different
face at a different optical size. One `--font-mono` token.

### 3.5 No line-height or font-weight system
`line-height` is set ad hoc in 8 places (1.2, 1.3, 1.35, 1.4, 1.5, 1.6) and inherited everywhere else.
Weights run 400/600/700/800 with no token. `.page-title` is 700, `.help-doc-page-title` is 800,
`.kpi-value` is 800 — three "heading" weights.

## Severity 4 — Accessibility. Largely absent.

### 4.1 Zero form labels are associated with their inputs
90 `<label>` elements. 119 `<input>`, 43 `<select>`, 5 `<textarea>`.
**`htmlFor`: 0. `id` on inputs: 0.**

No label in the entire application is programmatically tied to its control. Screen readers announce
"edit text, blank" for every field in the Wizard, Studio, Vault, Admin, and Login. Clicking a label
never focuses its input. `aria-invalid`: 0, `aria-describedby`: 0 — validation errors are never
associated with the field that failed. This is the single largest a11y gap and the most mechanical to fix.

### 4.2 Page titles are `<div>`s — the app has almost no heading structure
All **12** page titles are `<div className="page-title">`. Across the whole app:

`<h1>`: 2 (both in the Help doc reader) · `<h2>`: 1 · `<h3>`: 3 · `<h4>`: 0
`<main>`: 0 · `<header>`: 0 · `<section>`: 0 · `<aside>`: 0 · `<footer>`: 0 · `<nav>`: 1
`<fieldset>`/`<legend>`: 0 · `<dialog>`: 0

There is no document outline. Screen-reader users cannot jump between sections, and there is no
skip-to-content link. The 22 `<table>`s have **0 `<caption>`** and **0 of 127 `<th>` carry `scope`**.

### 4.3 59 interactive elements are keyboard-unreachable
59 `<div>`/`<span>`/`<a>`/`<tr>` elements carry `onClick` with neither `role` nor `tabIndex`. Concentrated
in Dashboard KPI drill-downs (`.kpi-value`, `.kpi-sub span`), Connected page row actions, Catalog tree,
Alerts, and Admin. Plus 5 `<a>` tags with `onClick` and **no `href`** — not focusable, not announced as
links, no middle-click/open-in-new-tab.

Aggregate a11y census: `aria-live` 0 · `aria-describedby` 0 · `aria-labelledby` 0 · `aria-current` 0 ·
`aria-selected` 0 · `aria-invalid` 0 · `aria-expanded` 2 · `role` 11 · `aria-label` 21.

`aria-current` being 0 means the active sidebar item is conveyed to assistive tech by nothing but color.

### 4.4 Toasts are never announced
`ToastNotification.jsx` has no `role="status"` and no `aria-live`. Every success, error, and warning in
the app is silent to a screen reader. It is also a **single slot** — a second toast overwrites the
first — dismisses after **2500 ms** with no manual dismiss and no pause-on-hover. 2.5 s is not enough to
read an error message, and errors in particular should persist until dismissed (WCAG 2.2.1).

### 4.5 Toast severity is inferred by regex over the message text
`contexts/ToastContext.jsx` — when a caller omits the type, `inferToastType()` regex-matches the message:

```js
if (/(fail|error|unable|cannot|...)/.test(m)) return 'error';
```

So `showToast("No errors found")` renders as a **red error toast**. `"Connection test — no failures"`
→ error. `"Required fields saved"` → matches `require` → error. Severity should be passed explicitly,
not guessed from prose.

### 4.6 Confirm dialogs focus the destructive button
`contexts/ConfirmContext.jsx` — for a non-prompt confirm, `inputRef` is attached to the **Confirm**
button, and the open effect calls `inputRef.current?.focus()`. So opening a `danger: true` dialog
("Delete this connection?") lands focus on **Delete**, and a stray Enter destroys the record. Destructive
dialogs should focus Cancel.

The dialog also has no focus trap (Tab escapes to the page behind), no focus restore on close, no
visible close control, and no `aria-describedby` linking the message to the dialog.

### 4.7 No reduced-motion, high-contrast, or print support
`@media (prefers-reduced-motion)`: **0** · `(prefers-contrast)`: **0** · `(forced-colors)`: **0** ·
`@media print`: **0**.

There are **6 infinite animations**, including `.status-dot.red{animation:pulse 1.5s infinite}` and
`.adapter-tile.error{animation:pulseCard 2s infinite}` — during an outage with 20 failing adapters, 40+
elements pulse continuously with no way to stop them (WCAG 2.2.2 / 2.3.3). `forced-colors` matters
specifically here: this is a Windows enterprise product, and High Contrast Mode will flatten a UI that
is already carrying all of its meaning in color. `@media print` matters because ops teams export
incident views to PDF.

### 4.8 Touch/click targets below the 24×24 minimum (WCAG 2.5.8)
| Element | Effective size |
|---|---|
| `.status-dot` (`cursor:pointer`) | **8 × 8 px** |
| `.map-actions button` (`padding:2px 4px`) | ~16 px tall |
| `.multi-field-chip button` (`padding:0 2px`) | ~14 px tall |
| `.add-field-btn` (`padding:2px 0`) | ~16 px tall |
| `.btn-ghost` (`padding:4px 8px`) | ~22 px tall |
| `.chip` (`padding:4px 12px`) | ~22 px tall |
| `.btn-sm` (`padding:5px 12px`) | ~24 px tall |

### 4.9 The global search is a broken combobox
`Topbar.jsx:179-198` declares `role="combobox"` + `role="listbox"` + `role="option"` but provides no
`aria-activedescendant` and **no arrow-key navigation** — options are reachable only by tabbing through
each one. There is also no empty state: when nothing matches, the dropdown is hidden entirely, so typing
a bad query produces silence. And no `Ctrl/Cmd+K` shortcut, which is table stakes.

## Severity 5 — Design-system integrity.

### 5.1 The spacing scale is defined, documented, and used once
`styles.css:41-45` defines `--space-1` … `--space-10` with the comment *"Use var(--space-N) instead of
magic numbers."* Total usage across the entire codebase: **2 references, 1 distinct token**
(`var(--space-5)`, in `.card`).

The actual spacing in use: inline `gap` values of 4, 6, 8, 9, 10, 11, 12, 14, 16, 20, 24 (11 values,
including off-grid 9 and 11) and 20+ distinct inline `padding` pairs (`6px 10px` ×18, `8px 12px` ×14,
`4px 8px` ×12, `6px 8px` ×9, `8px 14px`, `4px 10px`, `10px 14px`, `8px 10px`, `5px 8px`, `5px 6px`,
`5px 14px`, `5px 10px`, `2px 9px`, `1px 4px`, `9px 14px` …).

### 5.2 1,044 inline style objects

Inline styles cannot express `:hover`, `:focus`, `:disabled`, `:focus-visible`, or media queries. Every
control built this way is permanently stateless — which is why so much of the app has no hover or
pressed feedback.

### 5.3 `connected/styles.js` is a second, conflicting design system
A parallel JS style module that shadows the CSS one with different values:

| Token | `styles.js` | `styles.css` | Consequence |
|---|---|---|---|
| button padding | `6px 14px` | `8px 16px` | Connections buttons are shorter than every other button |
| button radius | `6` | `var(--radius)` = 8 | Different corner radius |
| button states | **none** | `:hover`/`:disabled` | No hover or disabled feedback at all |
| `thStyle` padding | `8px 12px` | `11px 16px` | Connections table is denser than every other table |
| `thStyle` transform | none | `uppercase` + `letter-spacing` | Different header treatment |
| input background | `var(--bg-main)` | `var(--bg-input)` | **Lavender-tinted inputs** in light theme |
| overlay z-index | `999` | `1000` | Connections modal sits below the confirm dialog… |
| overlay backdrop | `rgba(0,0,0,.45)` | `rgba(15,23,42,.45)` + blur | …and has no backdrop blur |

`overlayStyle.zIndex: 999` also **collides exactly** with `ToastNotification`'s `zIndex: 999` — toast/modal
stacking is undefined and DOM-order dependent.

### 5.4 12 border-radius values, 15 z-index values, 5 transition durations — no tokens for any
- **Radius:** tokens exist (`--radius-sm/--radius/--radius-lg`) and are used 49× in CSS, but hardcoded
  `1, 2, 3, 4, 5, 6, 8, 10, 12, 14, 16, 20px` appear alongside. In JSX: **96 inline `borderRadius`, only
  4 use a token** — `borderRadius: 6` appears **55 times** while `--radius` is 8.
- **Z-index:** 15 raw values (2, 5, 50, 90, 95, 100, 120, 125, 130, 200, 250, 300, 400, 500, 1000) plus
  999 in two JS files. No layer scale.
- **Transitions:** `--transition: 0.2s ease` exists, but `.25s`, `0.25s`, `.3s`, `.4s`, and `.15s`
  (in `styles.js`) all bypass it. No easing tokens.
- 7 `!important` declarations in the responsive overrides — a sign the fit-to-screen system and the
  breakpoints are fighting.

### 5.5 The icon system is Unicode dingbats mixed with color emoji
~370 icon glyphs across **99 distinct codepoints**, in two incompatible styles:

**Monochrome dingbats** (sidebar, `Sidebar.jsx:11-31`): `◉` Dashboard, `⚙` Registry, `⇄` Monitor,
`⚠` Alerts, `✎` Studio, **`⚩`** Wizard, `⇌` Canvas, `⚏` Catalog.

`⚩` (U+26A9) is the **horizontal male with stroke sign** — an intersex/transgender symbol — used as the
"Connection Wizard" icon. `⚏` (U+268F) is a *digram for greater yin*, used for "Entity Catalog". These
are arbitrary shape-matches with real meanings, and several render inconsistently or fall back to
tofu across Windows/macOS/Linux font stacks.

**Full-color emoji** (everywhere else): `🔗` Connections, `🔒` Vault, `👥` Admin, `📋` Jira, `📁` SharePoint,
`🗃` PostgreSQL, `🐬` MySQL, `🖥` SQL Server, `🏢` Dynamics, `📊` Excel, `📤` Export, `💾` Save, `🤖` Auto-Map.

So the sidebar is monochrome line-art and the toolbar directly below it is full-color emoji. Emoji also
render at OS-specific sizes and baselines, cannot be recolored, and never match a brand. A 20-icon SVG
sprite would replace all of it — and `public/icons.svg` shows the sprite plumbing was once there.

## Severity 6 — Information architecture and interaction.

### 6.1 The same object has three names
| Surface | Term |
|---|---|
| Dashboard | "Total **Adapters**", "**Adapter** Health" |
| Sidebar / Registry | "**Integration** Registry" |
| Connected page / Wizard | "My **Connections**", "**Connection** Wizard" |

Adapter, Integration, and Connection are the same entity. Pick one and change the other two.

### 6.2 Sidebar labels don't match page titles
| Sidebar | Page `<div class="page-title">` |
|---|---|
| Message Monitor | **"Trading Network Console"** |
| Entity Catalog | "Master Entity Catalog" |
| Alerts | "Alerts & Notifications" |

"Trading Network Console" is BizTalk vocabulary with no relationship to a Jira→SharePoint sync product.
A user who clicks "Message Monitor" lands on a page that appears to be something else.

### 6.3 Two date formats and two number conventions in one app
`connected/styles.js:fmtDate` hardcodes `toLocaleDateString('en-US', …)` → *"Jul 23, 2026 12:54 PM"*.
Every other surface (`MonitorPage`, `DashboardPage`, `DeadLetterPanel`, `AdminPage`, `RegistryPage`,
`integrationMap`) uses bare `toLocaleString()` → the *user's* locale. So on a non-US machine the
Connections page shows US dates and the Monitor page next to it shows local dates. No timezone is ever
displayed, which for a sync-audit tool is a genuine operational problem.

### 6.4 Status→color mapping disagrees between pages
`connected/styles.js` has no case for `PARTIAL` → falls through to `--text-dim` / `badge-neutral` (grey).
`DashboardPage.jsx:199` maps `PARTIAL` → `#f59e0b` (amber). The same push status is grey on one page and
amber on another. `statusColor` and `statusBadgeClass` in the same file also disagree with each other on
which strings count as success (`COMPLETED` vs `SUCCESS`).

### 6.5 Monitor pagination is over a 200-row client-side window
`MonitorPage.jsx` fetches `api.getMessages('?limit=200')` then paginates client-side at 50/page. The
"1–50 of N" counter can never exceed 200 and the maximum page count is 4 — so the UI silently claims to
show all messages while capping at the most recent 200. There is also **no column sorting** on any table
in the app (0 sortable headers across 22 tables), which is a baseline expectation for an ops console.

### 6.6 Expanded Monitor rows attach to the wrong message on refresh
`MonitorPage.jsx` keys row expansion as `` `${row.messageId}-${row.direction}-${idx}` `` where `idx` is
the index **within the current page slice**. Real-time polling runs every 4 s and prepends new messages,
shifting every index. An expanded payload therefore re-binds to a different message on the next tick.
Key by `messageId` alone.

### 6.7 Duplicated and triplicated controls
Monitor exposes **Export Logs** twice (page header + contextual toolbar), **Refresh** alongside a
**Real-time** toggle alongside a toolbar **Toggle Real-time**, and makes the whole row clickable *and*
adds a redundant "Payload" button that does the same thing — with no chevron or affordance indicating
the row is expandable.

### 6.8 Filter selection is indistinguishable from filter hover
`styles.css:488` — `.chip:hover, .chip.active{...}` share one identical rule. While the pointer is over
any filter chip, you cannot tell which one is actually selected. The chips are also `<span>`s with
`onClick` and no `aria-pressed`.

### 6.9 The brand mark reloads the page — and spins randomly
`Topbar.jsx:145` — clicking "Synapse" calls `window.location.reload()`, a full page reload that discards
all SPA state and re-downloads the 642 KB bundle. `title="Refresh"`. Universal convention is that the
logo navigates home.

`Topbar.jsx:146` — on hover, the logo rotates 180° in a **randomly chosen direction**
(`Math.random() < 0.5 ? 180 : -180`). Combined with `.icon-btn:hover{transform:scale(1.3)}` (a 30% jump
on every header icon), the app chrome is playful in a way that reads as consumer, not enterprise.

### 6.10 No error boundary and no 404 route
`App.jsx` has no `<ErrorBoundary>`. Any render error in any page white-screens the entire application
with no recovery path. `<Routes>` has no `path="*"` fallback, so a mistyped or stale URL renders the
full chrome around an empty content area with no explanation.

### 6.11 The user menu is not a menu
`.user-menu` is an avatar, a name, and an always-visible power-icon sign-out button. There is no
dropdown, no profile, no preferences, no theme setting, no session info. Sign-out is a single
unconfirmed click on a small icon. The nested-hover CSS
(`.user-menu:hover:not(:has(.icon-btn--signout:hover))`) is working around the fact that a button is
nested inside a hover-styled container.

### 6.12 The login screen is the weakest screen in the app
`components/auth/LoginPage.jsx` — the first thing a buyer sees:
- No logo or product mark; just the word "Synapse" at `1.4rem`.
- No SSO option, no "Forgot password", no "Remember me".
- No show/hide password toggle — despite `.password-wrap .eye-btn` existing in the design system.
- Labels not associated with inputs (clicking "Email" does nothing).
- Error rendered as a bare red `<div>` with no `role="alert"` — a failed login is silent to a screen reader.
- Submit is disabled until both fields are non-empty, with no explanation of why it's dead.
- No caps-lock warning, no lockout/rate-limit feedback.
- `minHeight: '100vh'` inside a `height: 100dvh; overflow: hidden` body — the card can clip on mobile.
- No theme toggle, so the user is locked into whatever theme loads.

### 6.13 `100vh` used where the body uses `100dvh`
`body` correctly uses `height: 100dvh`, but `.help-panel{height:100vh}`, the mobile `.sidebar{height:100vh}`,
the mobile `.detail-pane{height:100vh}`, and `LoginPage`'s `minHeight:'100vh'` do not. On mobile browsers
with dynamic chrome these overflow the visual viewport, pushing their bottom controls off-screen.
