2. Module Overview
2.1 Purpose
Connector Studio is the design-time workspace where a Designer onboards a new external system into the Synapse platform. It is a one-time activity per system type. Once a connector template is published, Operators can create unlimited integration instances without Designer involvement.

The current implementation (StudioPage.jsx) renders the UI shell with all action buttons disabled (line 86). This FSD defines the full functional behaviour required to make the module production-ready.

2.2 Personas
Persona
Role
Primary Actions in Studio
Designer
Integration Engineer / Developer
Create, configure, test, publish connector templates
Administrator
IT Admin / Platform Owner
View published connectors, manage versions, deprecate
Operator
Business Analyst / Team Lead
Read-only: browse published connectors in Registry only

2.3 Sub-flows
System Registration — Select category, name the connector, provide base config
Authentication Configuration — Define auth method and credential schema
Operation Selection — Choose/discover available operations (read/write/both)
Entity Modelling — Group raw fields into labelled entities, link to Master Catalog
Test &amp; Validate — Run live test call with sample credentials
Publish &amp; Version — Clone-on-publish, immutable past versions

6. Operation Selection &amp; Tagging
After authentication is configured and a successful Test Connection is made, the Studio presents the discovered or manually-entered operations.

Field / Control
Behaviour
Operation List
Auto-populated from OpenAPI spec / DB introspection / WSDL parse / GraphQL introspection. Manual entry available as fallback.
Direction Tag
Each operation tagged Read, Write, or Both. Controls whether it appears as a Source operation, Destination operation, or either in the Wizard.
Operator Visibility
Toggle per operation. Hidden operations are excluded from the Wizard but remain available to Designers for testing.
Entity Assignment
Link each operation to an Entity defined in Section 7. Required before publish.
Sample Data Preview
For Read operations: fetch up to 5 real records to preview field names and data types. Required for Mapping Canvas to auto-suggest.
Rate / Quota Notes
Free-text annotation Designer adds to warn Operators (e.g. &apos;API quota: 1000 req/day&apos;).

7. Entity Modelling
Entity Modelling groups raw operation response fields into human-friendly, reusable entities that live in the Master Entity Catalog and drive the Mapping Canvas.

Step
Action
Detail
1
Auto-infer schema
From sample data fetch (§6) or spec, infer field names, data types, and nullability.
2
Rename fields
Designer maps technical field names to human labels (e.g. issue_key → Ticket ID).
3
Group into entity
Drag fields into a named entity (e.g. &apos;Jira Issue&apos;, &apos;Sprint&apos;, &apos;Project&apos;).
4
Assign canonical type
Map each field to a canonical type: string / number / boolean / datetime / json / rich_text / attachment.
5
Link to Master Catalog
Optionally link this entity to an existing Master Entity Catalog entry, or create a new entry.
6
Mark required fields
Flag fields that must be mapped for an integration to be valid (blocks Wizard Publish if unmapped).
7
Set PK / Natural Key
Designate the field used as the natural key for upsert deduplication (e.g. jira_key, ticket_id).

8. Test &amp; Validate
A connector cannot be published until at least one successful test call completes. The test sub-screen is shown inline within the Studio flow.

Check

Fail Behaviour

9. Publish &amp; Version
Publish creates an immutable snapshot stored in connector_versions (clone-on-publish pattern).
Version number auto-increments: MAJOR.MINOR.PATCH. Designer can override MAJOR on breaking changes.
Existing integration instances pinned to prior version; Operators see &apos;Upgrade available&apos; badge.
Deprecation: Designer marks a version deprecated with a sunset date; running instances show warning.
Rollback: Administrator can revert published version to any prior version; triggers re-test gate.

13. Acceptance Criteria (Definition of Done)
Selecting REST API + uploading OAS 3.0 spec auto-discovers all endpoints and lists them as selectable operations with direction tags.
Selecting Database + connection string introspects the schema and lists tables and columns.
Selecting GraphQL endpoint + introspection query discovers schema and generates operation list.
Each operation can be tagged Read / Write / Both and toggled visible/hidden for Operators.
Connector cannot be published until Test Connection returns pass; Publish button remains disabled otherwise.
Publish creates an immutable connector_versions record; version number increments correctly.
Updating a published connector creates a new version; running integration instances stay on prior version with an upgrade badge shown.
Clone Template creates a new draft connector pre-populated with all fields of the source.
Import Spec accepts OAS 3.0 JSON/YAML, WSDL URL, and GraphQL SDL file.
All 8 production categories render their correct dynamic auth sub-form with the fields defined in §5.
Entity Modelling: fields can be renamed, grouped, typed, and linked to Master Catalog entities.
Connector Studio page loads with all 3 action buttons (New Connector, Import Spec, Clone Template) functional.
